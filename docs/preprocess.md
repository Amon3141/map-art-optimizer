# 道路グラフ前処理（H0）

本書は、最適化パイプライン全体のうち **H0（前処理）** を、実装・レビュー・別エージェント参照用に **自己完結**する形でまとめたものである。

**関連ドキュメント**

- 最適化のプロダクト要件・制約の全体: [optimization.md](./optimization.md)（特に 4.1 道路ネット、座標系、グラフのイメージ）
- OSM 取得経路: [architecture.md](./architecture.md)（Overpass を FastAPI がプロキシ）
- 確定した横断判断の時系列: [decisions.md](./decisions.md)

**用語**: 本文中の **H0-a〜H0-e** は、内部設計メモ（最適化ヒューリスティック計画）と同じ区分に揃えている。

## 1. H0 の目的とスコープ

### 1.1 何のための前処理か

後続（未実装）の最適化は、手書きストロークに **位置・回転・スケール・鏡映** を与え、**道路グラフ上の単一連続パス**として「形」を再現する。H0 はそのために、Overpass 等から得た OSM データを **計算用の平面座標上のグラフ**にし、**最近傍クエリなどが現実時間で回る状態**に整える。

### 1.2 いつ実行するか（キャッシュの考え方）


| 種類                                  | 内容                                        |
| ----------------------------------- | ----------------------------------------- |
| **まとめて一度（または bbox / OSM 応答が変わるたび）** | OSM パース、平面投影、グラフ構築・（任意）軽量化、空間索引構築、許可辺フィルタ |
| **リクエストごと（ストローク単位）**                | 投影パラメータの確定、ストローク点列の平面化、索引への問い合わせ          |


**同一探索エリア・同一 OSM スナップショット**であれば、グラフ構築から索引まで **キャッシュ**でき、再試行時の体感が大きく改善する。キャッシュキーは少なくとも **探索 bbox（または正規化したキー）＋ Overpass 応答のハッシュ**を想定する。

### 1.3 実装フェーズの位置づけ

バックエンドは数段階で進める想定である。**最初のマイルストーンは H0 前処理のみ**にフォーカスし、ここを丁寧に仕上げる。最適化（変換探索・スコアリング等）は後続フェーズとする。

## 2. H0-a — 平面投影（メートル座標）

[optimization.md](./optimization.md) 4.1 にある通り、距離・スナップ・類似度などの幾何は **局所平面座標（メートル）** で扱い、**WGS84 のまま距離と角度を混ぜない**。

### 2.1 決定事項（要約）

- **採用する投影**: **Local tangent plane**（探索 bbox の中心緯度でスケールした局所平面近似。例: `x = R·cos(lat0)·Δlon`, `y = R·Δlat`、R は地球半径、`lon0,lat0` は bbox 中心）。
- **根拠**: 探索 bbox は **多くても数十 km オーダー**を想定する。プロダクト上、**目標距離に厳密に寄せること**や **m 単位の絶対距離精度**は第一優先ではない（緩い目標・許容でよい）。
- **帰結**: このスコープでは **azimuthal equidistant や UTM への切り替えは必須ではない**。将来、距離制約や bbox を厳しくした時点で H0-a を見直してよい。

### 2.2 ストロークとの一貫性

キャンバス上の正規化点列を地図 bbox 上に置くときも、道路グラフと **同じ投影**で平面座標に落とし、その上で回転・スケール等を適用する。

## 3. H0-b — OSM からグラフへ（トポロジ・接続・交差）

**最小構成**: OSM の `way` を折れ線として読み、**ノード＝交差点・端点**、**辺＝（分割後の）セグメント**として扱う。接続規則・交差処理は以下の要件 B1〜B3 で決める。

### B1 — OSM node id の信頼性と距離ベース併用

- **id のみで接続**すると、別 way が同一交差点で **共通ノードを持たない**場合にグラフが切れる。また後述 B3 の問題と結びつき、「角で曲がれない」制約が出やすい。
- **方針**: デバッグ画面で **id ベース接続のみのグラフ**を可視化し、実データ上 **どの程度使えるかを確認したうえで**、距離ベース併用の強さ（閾値 ε、対象は端点のみか等）を決める。
- **仮説**: id が **実用上ほぼ完璧でない限り**、**距離ベースの近接ノード／端点スナップ**（閾値 ε）を入れる可能性が **高い**。
- **誤接続抑制**: ε は一律にせず、`highway` 種別に応じて変える、OSM の `**layer` / `level` / `bridge` / `tunnel`** 等があれば **異なるレイヤ同士をマージしない** 等のガードを検討する（B2 と連動）。

### B2 — 立体交差・橋（誤接続の抑制）

- **望ましい挙動**: 橋・高架と下の道路のように **本来つながらない**ものは、できるだけ **グラフ上も接続しない**。
- **優先度**: 実装が難しければ **優先度は低め**でよい。本アプリの主目的は **地図アート作成**であり、立体交差の完全除外が **技術的に困難またはコスト過大**な場合、意図したスコープの例外として許容する（エッジケース）。

### B3 — 道路交差の幾何検出と split（製品差別化として重視）

**背景（なぜ必要か）**

OSM では、十字のように交わる縦道 `A–B` と横道 `C–D` が、**交点 E で共通ノードを持たず**、二つの独立した `way` として登録されていることが多い。このままグラフ化すると、交点 E を **グラフのノードとして表現できず**、例えば `**A–E–D` のようなジオメトリ**（交点で「曲がる」表現）が取れない。地図アートのように **形**を道路に沿わせる用途では、交点での自由度が効く。

**要件**

1. **道路同士の交差を幾何的に検出**する（別 way の線分同士が交わる点）。
2. 交点で辺を **分割**する。例: `A–B` → `A–E`, `E–B`；`C–D` → `C–E`, `E–D`。
3. 交点 E は **新規ノード**（平面座標上の交点座標）として保持する。
4. 元の `way` id、`highway=*` 等のタグは **エッジ属性**に引き継ぎ、デバッグ・ペナルティ設定に使えるようにする。

**実装・設計上の未確定メモ**（実装時に具体化する）

- セグメント–セグメントの交差判定、**ほぼ平行・近接のみ**の誤検出除外。
- **端点一致**（id マージや距離スナップ）で既にトポロジが閉じている場合との **統合順序**（split 前後どちらで id マージするか等）。

**実装済み（デバッグ用）**: bbox・辺数が大きい場合の交差候補絞り込みとして、`app/osm/graph_build.py` に **Shapely STRtree（セグメント bbox の重なりで候補列挙）** を入れた（詳細は §6.1）。

### B4 — 不要な中間ノード削除（オプション・グラフ構築の最終段）

実験の結果、way 入力段階での「重複・冗長ジオメトリ除去」は採用しない。代わりに、**平面グラフができたあと**（OSM id マージ・交差 split・ε スナップの **すべてのオプション適用の後**）にのみ、次の **次数 2 チェーン簡略化**をオプションで実行する（`remove_redundant_chain_vertices`）。

- **削除しない**: `source_osm_node_ids` が空の **synthetic** 頂点、`merged_from_osm_id` または `merged_from_snap` が真の頂点（id／ε 結合点）、`is_way_polyline_endpoint` が真の頂点、次数 ≠ 2 の頂点。
- **削除候補**: 上記以外で次数 2 かつ入射 2 辺の **`osm_way_id` が同一**の頂点に限る。
- **幾何（符号付き累積角）**: チェーンを端から一方向に走査し、各削除候補頂点での折れを **符号付き角**（進行方向 `P[i−1]→P[i]→P[i+1]`、`atan2(cross, dot)`、退化辺は 0）として **累積**する。**累積の絶対値**が閾値 **約 15°**（実装は `_PRUNE_ACCUM_THRESHOLD_RAD`）以上になった頂点を **サンプルとして残す**。超過分は **符号に沿って閾値の整数倍を差し引き**（累積のモジュロ）、残りを次の区間の累積の初期値とする。これにより **一頂点あたりの折れが小さくても** **同符号で積み上がる緩いカーブ**に中間頂点が残り、弦一本への潰れを防ぐ。一方、**符号が打ち消し合う左右振れ**では累積が閾値に届きにくく、遠視で直線に近い見え方として潰しやすい。マージで新設する辺の `polyline_xy_m` は **残した両端点の弦（polyline 2 点）** とし、潰れた区間に含まれていた折れ細部の座標列は連結して保持しない（可視化と「中間ノード除去」の意味を一致させる）。同一 uv 間に複数辺があればすべて削除対象に含める。計算量はチェーン長に線形（頂点あたり `atan2` 1 回程度）。
- **閉路**: 成分が「すべて削除候補のみの閉路」のときは簡略化をスキップする（レア）。

### H0-c との順序

**degree-2 chain collapse** を含む **グラフの軽量化・内部保持形式**の詳細は、**H0-b（B1〜B3）の方針が固まってから**議論・確定する。split 後の次数分布や、元 polyline をエッジに保持するか等に影響するためである。上記 B4 のオプションは、デバッグ用パイプラインで H0-b 後段として実装済み（§6.1）。

## 4. H0-c — グラフの軽量化（degree-2 chain collapse）

**注意**: 上記の通り、**H0-b が固まるまで**、縮約の有無・属性マージの細部は **確定しない**。以下は候補比較のメモである。

**内容（候補）**: 次数 2 の中間ノードを列ごとに潰し、**長い一本のエッジ**にまとめる。元の折れ線の **総長**、`**highway=*`** 等はエッジ属性として保持する（縮約列内でタグが矛盾する場合の代表値ルールは別途決める）。


| 方針        | メリット                            | デメリット                                                         |
| --------- | ------------------------------- | ------------------------------------------------------------- |
| **縮約する**  | ノード数・最短経路の展開が激減。最近傍スナップの対象辺も減る。 | 中間頂点が消える。**形状スコアで元の曲がり**を見たい場合は、エッジに **元座標列**を持つ等の補償が必要になりうる。 |
| **縮約しない** | 形状とグラフが 1:1 に近い。                | 都市部で辺数が爆発しやすく、後続の **時間制約**に効く。                                |


**属性マージの例**（縮約する場合、列内で `highway` が混在するとき）

- **(a) 最悪ペナルティを代表値にする**（保守的）
- **(b) 長さ加重平均**
- **(c) 細い道が 1 本でも混じれば列全体にペナルティ**

走行性を後から調整するなら **(a) または (c)** が安全になりやすい。

## 5. H0-d — 許可辺フィルタ（削除 vs コスト）


| 方針                       | メリット           | デメリット                      |
| ------------------------ | -------------- | -------------------------- |
| **構築時に非対象 way をグラフから削除** | グラフが小さく、探索が単純。 | 道種のチューニングのたびに **再構築**しやすい。 |
| **辺は残し、超大ペナルティで事実上禁止**   | デバッグ・A/B が容易。  | グラフ規模は大きめのまま（索引・縮約で緩和）。    |


**決定事項**: 一旦、highway = **motorway のみ削除、それ以外は含める。**

## 6. H0-e — 空間索引と bbox クリップ

後続の「各ストローク点 → **最近傍道路辺**」が **O(辺数 × 点数)** だとすぐ破綻する。各辺の **軸平行バウンディングボックス**を索引に登録し、候補だけ詳細距離を計算する。


| 方式                             | メリット                 | デメリット                                   |
| ------------------------------ | -------------------- | --------------------------------------- |
| **Uniform grid（ハッシュグリッド）**     | 実装が短い。依存ゼロにしやすい。     | **セルサイズ**のチューニング。極端に長い辺は複数セルにまたがる処理が必要。 |
| **R-tree（Shapely STRtree）** | 辺密度が不均一でもクエリが安定しやすい。 | ライブラリ依存・構築オーバーヘッド。                      |


**意思決定**: **本リポジトリのバックエンド（`graph_build.py`）では STRtree を採用**する（`shapely` / `numpy` を `requirements.txt` に固定）。

**bbox クリップ**: Overpass で取得した **探索 bbox 外**の辺は、索引に入れないか、クエリ対象から外す。メモリと索引サイズを抑える。

### 6.1 実装メモ（デバッグ用グラフ構築 `app/osm/graph_build.py`）

FastAPI の **`/api/debug/graph-preview`** から呼ばれる、OSM GeoJSON → 平面グラフ → 可視化用 GeoJSON までのパイプラインにおいて、**H0-e に沿った Shapely STRtree** を用い、大きな way 数でも素朴な全対全にならないようにしている。

| 処理 | 要点 |
| --- | --- |
| **ε スナップ**（距離が近い頂点をまとめる・UI 表記はそのまま） | 各頂点を **Point** として STRtree に登録し、`dwithin(ε)` で近傍候補を列挙。**`oid > nid`** のときだけ union-find を検討（重複ペア回避）。**結合するのは次を両立するときのみ**: (1) 二点が **どちらか一方でも OSM 折れ線の端点**である、(2) 二点が **同一グラフ辺の両端ではない**（隣接セグメントの端点同士・同一直線上の近接のみを除外）。中間頂点同士は結合しない。更新は **OSM id マージと同型**：成分ごとに代表頂点・属性集約を決め、`rem` で端点を **一括 remap** し、**辺集合は 1 回スキャン**。空間索引まわりの計算量はおおよそ **O(n log n)** とクエリ **O(log n + k)**（k = ε 内の近傍点数）、グラフ側は **O(n + E)**。 |
| **交差 split** | 全エッジの折れ線をセグメントに分解し、各セグメントを **LineString** として STRtree に登録。**軸平行 bbox の重なり**（木の既定クエリ）で候補ペアを列挙し、`edge_id` の sort rank と `(e1,s1,e2,s2)` で安定ソートしたうえで、厳密な内部交差は既存の `segment_intersection_interior`。交点が見つかるたびにグラフが更新されるため、索引は **反復ごとに再構築**。セグメント数 S に対し構築はおおよそ **O(S log S)**（実測では way 数・セグメント数が多い bbox でもセル幅チューニングなしでスケール）。 |
| **OSM node id マージ** | 同一 OSM id にぶら下がるグラフ頂点を **union-find で連結成分化**し、代表頂点（id の辞書順最小等）と属性集約を決めたうえで、**辺集合を 1 回スキャン**して端点を remap（逐次の全辺 dict 再構築ループは廃止）。`step_metrics.connect_osm.osm_id_groups_merged` は **初期グラフで「2 つ以上の頂点に現れた OSM id」の個数**。 |
| **不要な中間ノード削除**（オプション） | `remove_redundant_chain_vertices` が ON のとき、ε スナップの **直後**に実行。次数 2・同一 `osm_way_id`・保護なしのチェーンを列挙し、**符号付き折れ角の累積の絶対値**が約 15° を超えた頂点を残して辺をマージ（超過分は符号付きモジュロでリセット）。マージ後の各辺のジオメトリは **残した両端点の弦（polyline 2 点）** とし、同一 uv の重複辺はまとめて削除する。`/api/debug/graph-preview` の GeoJSON は **簡略化後の頂点・辺のみ**を返す。 |
| **GeoJSON 出力** | 頂点の `vertex_role` 等のため、**辺から隣接リストを O(E)** で構築し、次数 2 の頂点で入射辺 2 本を全辺走査しない。 |

**未実装・今後の伸びしろ**: ストローク点列向けの **永続 spatial_index** オブジェクトとしての公開、キャッシュ（1.2 節）、交差処理の **一括列挙＋一括分割**（反復回数そのものの削減）は別タスク。

## 7. H0 の成果物（インターフェースの目安）

後続ステップ（スナップ・経路探索・スコア）が期待する **不変に近い契約**の例:

- `**nodes`**: 内部ノード id → 平面座標 `(x_m, y_m)`。
- `**edges`**: `u`, `v`, `length_m`, `highway`, その他ペナルティ用属性。オプションで **元の折れ線の座標列**（形状評価・デバッグ用）。
- `**spatial_index`**: 辺 id に対する最近傍（または矩形内候補）クエリ。
- `**proj`**: 平面 → **WGS84** の逆変換（API 正は GeoJSON の `[lon, lat]`。決定事項は [decisions.md](./decisions.md)）。

## 8. 性能・時間予算との関係（メモ）

H0 は **2 秒優先・最大約 10 秒**の最適化全体バジェットのうち、**毎リクエストまたはキャッシュミス時**に支払うコストになる。グラフが大きい探索エリアでは **縮約（H0-c）・索引（H0-e）・許可辺の削減（H0-d）**がないと、後続が詰まりやすい。
